# OnMyWay AI: 퇴근길 완료 플래너

공식 출처 재확인·설명회 반영일: 2026-11-03 KST. 기존 영상·음성 증거와 이번 FusedLocation 구현·공식 AVD 확인·테스트 재실행을 구분하며 개발 기록에 남깁니다. 아래에서 **공식 확인**, **구현·검증**, **가설·계획**을 구분합니다. [설명회 근거와 보완 순서](submission/briefing-review-ko.md)를 참조합니다. 수상 가능성을 점수나 확률로 추정하지 않습니다.

## 선택한 고객과 문제

**귀가 마감이 있는 자동차 출퇴근 운전자**를 초기 고객으로 좁힙니다. 약 구매와 세탁물 수령처럼 꼭 끝낼 일 2개, 여유가 있으면 할 장보기 1개를 퇴근길에 처리하는 상황입니다. 가족과의 저녁 약속 등 귀가 이유는 사용자가 정하며 수집하지 않아도 됩니다.

문제 가설은 “어디가 가까운가”보다 “꼭 해야 할 일을 마치고 제시간에 집에 갈 수 있는가”를 판단하기 어렵다는 것입니다. 주 2~3회 반복 수요는 아직 조사하지 않은 가설입니다. 인터뷰·현재 고객·시간 절감 실측은 없습니다.

넓은 생활 비서 대신 **요청 확인 → 마감 판단 → 다음 목적지 승인 → 정차 후 완료 → 남은 일정·귀가**에 집중합니다. 차량특화성은 이동 중 대화를 길게 하는 데서 얻지 않습니다. 정차 중 의사결정과 차량 내비 연결, 실제 주행 제한을 한 흐름에 묶는 데서 얻습니다. 기존 제품명은 유지하고 발표의 설명을 이 문제로 좁힙니다.

## 사용자의 대안과 포지셔닝

| 대안 | 확인한 사실 또는 명시한 가설 | OnMyWay AI가 검증할 가치 |
| --- | --- | --- |
| 지도 다중 경유지 | [Google Maps 공식 도움말](https://support.google.com/maps/answer/144339?hl=en)에 여러 목적지 추가·순서 변경이 있음 | 목적지를 등록하는 수고에 더해 필수·선택·수령 완료 마감과 귀가를 검토하는 흐름이 실제로 유용한가 |
| 전문 경로 최적화 | [Route4Me 공식 설정](https://support.route4me.com/route-settings/)은 시간 창·서비스 시간·경로 종료 지점을 지원 | 전문 배차의 최적화 기능을 복제하는 대신 개인 운전자의 짧은 요청과 정차 중 한 단계 판단에 집중할 가치가 있는가 |
| 메모 + 개별 검색 | 사용자가 직접 조건을 기억하고 검색할 수 있다는 대안 가설. 사용 빈도는 미측정 | 동일한 가상 과제로 누락·잘못된 확신·조작 수를 비교하고 불필요한 질문이 늘지 않는지 확인 |

다른 제품 전체나 국내 내비의 미지원 기능을 확인했다고 주장하지 않습니다. 방어 가능한 차별점은 기능 독점이 아니라 특정 고객의 완료 흐름과 차량 상호작용을 연결한 구현입니다.

## AI와 시간 계산의 책임

LLM 연결 경로는 요청·답변에서 용무와 조건을 구조화합니다. 사용자는 원문과 해석을 비교·수정하고 빠진 귀가 시간을 직접 정합니다. 답변 재해석에서 필수 용무 누락·교체·선택 격하는 거부하며, 기존 체류나 마감을 완화하는 출력은 보수적으로 보존하고 경고합니다. 의도적인 완화는 사용자 편집·승인으로 처리합니다.

계획 엔진은 도로 이동 + 영업 시작 대기 + 체류 + 귀가 구간을 합산합니다. 정보 부족은 실행 가능과 다릅니다. 근거 설명은 실제 계산 결과에서 만들며 추가 LLM 추측을 쓰지 않습니다. 현재 네이티브 앱은 Kakao 검색 후보 최대 세 개에서 사용자가 정확한 점포를 고정하고, 직접 확인한 이용 시간·수령 가능 여부와 근거·시각을 별도로 기록합니다. 검색 결과 자체는 영업시간·서비스 가능 여부를 제공하지 않습니다. 키를 넣는 것만으로 실제 서비스 출시가 끝나지 않습니다.

키 없는 데모의 문장·해석·장소·이동시간은 독립적으로 선택한 예시이며 안내와 도착은 모의 이벤트입니다. 실제 STT·LLM 결과가 아닙니다. 실제 경로 호출 실패를 예시로 바꾸지 않습니다.

## 차량 UI와 SDK 적용 판단

[Pleos 주행 설계](https://document.pleos.ai/docs/pleos-only/vehicle-app-planning-guide/driver-distraction-guideline)는 CarUxRestrictions에 따른 제한과 단순한 조작을 요구합니다. [디자인 가이드](https://document.pleos.ai/docs/connect/guide/docs-design/Introduction/intro)는 일관성·가독성·주야간 대응을 제시합니다. 현재 앱은 중립 바탕과 대비, 큰 하단 행동 버튼, 축약 원문·펼쳐 보는 상세, 한 번에 한 질문, 시스템 주야간 테마를 사용합니다. 실제 화면을 확인했지만 물리 단위의 가독성 인증이나 플랫폼 심사 통과를 주장하지 않습니다.

[개발 안내](https://appdevchallenge.auto-hmg.io/guide/development)와 [FAQ](https://appdevchallenge.auto-hmg.io/faq)의 SDK 제공 목록을 실제 사용 목록과 혼동하지 않습니다. STT 3.3.1·TTS 3.3.1 ON_DEVICE와 NaviHelper 3.0.5를 연결했고 차량 제한은 Android Car API로 읽습니다. 실제 한국어 출력은 [음성 증거](screenshots/spoken-plan/README.md), 내비 화면 전환과 빈 지도 한계는 [내비 증거](screenshots/navigation-handoff/README.md)에 있습니다. FusedLocation 1.1.3의 최신 위치 수신·출발지 확인·집 저장과 거부/주행 경계를 공식 AVD에서 검증했습니다. [위치 설정과 한계](location-setup.md)를 참조합니다. Vehicle SDK·Gleo는 현재 미사용입니다. [설명회 32:02](https://www.youtube.com/watch?v=na6tSJ44pWc&t=1922s)의 취지처럼 SDK 수보다 필수 완료 흐름에 필요한 기능을 우선합니다. 주행 중 음성 입력 허용이나 사용자 승인 없는 목적지 전송을 추가하지 않습니다.

설명회는 개발 단계의 manifest 권한 선언과 App Market 배포 시 권한 심사를 구분합니다. 실제 서비스의 HTTP 401이나 미지원 상태를 권한 승인 대기로 단정하지 않습니다. 외부 API·네트워크 이용 허용도 실제 제공자 호출 성공을 뜻하지 않습니다.

## 확보·반복 이용·사업 가설

초기 확보는 사용자 승인 후 차량 출퇴근 커뮤니티에서 소규모 파일럿 참가자를 모집하는 계획입니다. 현재 모집·접촉·외부 메시지는 수행하지 않았습니다. 첫 사용 계기는 그날의 마감 있는 픽업이며, 반복 이유는 남은 일정과 귀가 조건을 한 번에 다시 판단하는 가치라는 가설입니다. 즐겨찾는 루틴·동승자 일정·충전 대기 용무는 검증 이후 확장 후보입니다.

다음은 **실적이나 공식 목표가 아닌 계산 예시**입니다. 월 대상 도달 200명 × 설치 50% × 첫 계획 완료 60% = 월 신규 활성 60명. 월별 재사용 비율을 r로 놓고 M(t)=60+r×M(t−1), M(0)=0으로 단순 계산합니다. 기존 문서의 대규모 노출 가정 대신 작은 파일럿을 설명하기 위한 보수적인 규모입니다.

| 가정 r | 1개월차 MAU | 2개월차 MAU | 3개월차 MAU |
| --- | ---: | ---: | ---: |
| 20% | 60 | 72 | 약 74 |
| 40% | 60 | 84 | 약 94 |
| 60% | 60 | 96 | 약 118 |

월별 활성 재사용은 코호트 D7·D30 리텐션과 다른 지표입니다. 중복 유입·휴면 복귀를 생략한 모델이며 시장 규모 예측이 아닙니다. 코호트 리텐션은 첫 핵심 계획을 완료한 사용자 중 지정 기간에 다시 핵심 계획을 수행한 비율로 별도 측정합니다. 원문·좌표·음성 없이 필요한 이벤트만 수집할 동의·정책을 먼저 마련합니다.

출시 전 사용자 승인 파일럿 계획: 5~8명의 과제 관찰로 질문·원문 수정·완료 버튼의 이해를 먼저 확인하고, 이후 20명 규모 2주 사용에서 첫 계획 활성, 필수 완료, D7 재사용, 잘못된 가능 판정과 선택 제외 이해를 기록합니다. 모집·표본수·기간은 제안이며 수행 사실이 아닙니다. 출시 판단은 인터뷰만으로 하지 않고 데이터 누락·필수 보존·주행 차단의 오류가 없는지 함께 봅니다.

초기 과금은 미정입니다. 추후 저장 루틴 등 편의 기능의 구독 지불 의사를 검증하고 사용자당 모델·경로 호출비를 계측합니다. 월 공헌이익은 결제액−스토어 수수료−모델·지도 호출비−운영비로 계산하되 지금 매출을 예측하지 않습니다. 제휴 픽업은 계약·재고·영업정보 신뢰성이 확보된 뒤 고려하며 현재 제휴는 없습니다. 광고나 제휴 수익이 필수 일 우선순위를 바꾸면 안 됩니다.

## 출시까지의 순서와 통과 조건

1. **현재 데모**: 키 없이 명시된 예시 → 세 용무 완료 → 별도 귀가, 촉박한 조건 승인·재계산, 주행 차단. 최신 APK·영상·자료를 서로 일치시킵니다.
2. **실제 데이터 검증**: 사용자가 서버에 키를 설정한 뒤 모델 답변, 좌표·도로 응답·지연·오류를 확인합니다. 영업·수령 가능 여부와 시간의 출처·확인 시각을 확보하고, 모르면 확인 필요를 유지합니다. 네이티브 검색의 최대 세 후보·사용자 선택과 계획기의 탐색 범위를 설명합니다.
3. **플랫폼 검증**: 공모전은 실차 시연을 지원하지 않고 공식 에뮬레이터로 검증합니다([21:04](https://www.youtube.com/watch?v=na6tSJ44pWc&t=1264s)). PT 전 최종 STT·지도 표시·NaviHelper 수락·동일 이름 콜백·도착과 실패 복구를 검증합니다. 물리 차량의 화면 거리·햇빛·주야간·차종·지역·카테고리 사용성은 실제 출시 전 별도 과제로 둡니다.
4. **개인정보·운영**: 현재 신뢰된 로컬 개발 서버를 공개 서비스로 노출하지 않습니다. 운영 인증·TLS·요청 제한·장애 관측·지원·데이터 삭제 정책, 공유 차량의 운전자 교체·세션 분리를 출시 전에 마련합니다. 원문·집 좌표 보관을 최소화하고 원시 음성 보관은 기본값으로 도입하지 않습니다. [공식 개인정보 설계](https://document.pleos.ai/docs/pleos-only/vehicle-app-planning-guide/security-privacy)를 적용하되 법률 검토 완료로 표현하지 않습니다.
5. **수요·경제성·배포**: 승인된 사용자 검증 후 효용·재사용·호출비·지불 의사를 보고 배포 여부를 결정합니다. App Market 입점은 별도 심사·차종·지역 조건이 있으며 보장되지 않습니다.
